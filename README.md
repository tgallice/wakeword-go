# wakeword-go

A wake word detector in pure Go, running the [microWakeWord](https://github.com/kahrendt/microWakeWord)
v2 models that ESPHome and Home Assistant use, with no CGO and no native dependency.

It contains a minimal TFLite interpreter (thirteen int8 operators, exactly the set those
models need), a port of the tflite-micro audio frontend, and the ESPHome decision logic.
Everything is bit-exact with the reference: the interpreter reproduces the TensorFlow Lite
reference kernels and the frontend reproduces the C microfrontend, and the test suite
checks both by strict equality against golden vectors generated by the original code.

## Invariants

- **Pure Go.** `CGO_ENABLED=0 go build ./...` always works. The only dependency is the
  FlatBuffers Go runtime. Cross-compiling to any platform Go supports is a plain `GOOS=... go build`.
- **Bit-exact int8 arithmetic.** Same integer types, rounding and saturation as
  `tensorflow/lite/kernels/internal/reference` and tflite-micro. No float where the reference
  uses integers. The parity tests compare 13,200 model invocations and 63,360 frontend feature
  values with the reference outputs, with zero tolerance. An end-to-end check over the whole
  synthetic corpus (782 files, 310,316 chained frontend-to-model invocations) against
  `pymicro-features` + `ai-edge-litert` in `BUILTIN_REF` mode found 2 differing probabilities,
  both far below any cutoff: the detections are identical at every threshold tested.
- **Nothing hardcoded from the model.** Shapes, quantization, variable state, the
  initialization subgraph and the detection thresholds are all read from the `.tflite` file
  and its JSON manifest. Any microWakeWord v2 model loads unchanged.
- **Explicit rejection.** An unsupported operator, version, dtype or option fails at load time
  with an error naming it. There is no silent fallback.

## Supported models

The five official v2 models are in `testdata/models/v2`, pinned to a commit of
[esphome/micro-wake-word-models](https://github.com/esphome/micro-wake-word-models) (Apache 2.0,
by Kevin Ahrendt): `alexa`, `hey_jarvis`, `hey_mycroft`, `okay_nabu` and the `vad` model.

Any other model trained with microWakeWord v2 should load as is: it needs the same thirteen
operators (CONV_2D, DEPTHWISE_CONV_2D, FULLY_CONNECTED, LOGISTIC, QUANTIZE, CONCATENATION,
STRIDED_SLICE, SPLIT_V, RESHAPE and the variable operators), an int8 `[1, stride, 40]` input
and a uint8 `[1, 1]` output. To add one, put the `.tflite` next to its `.json` manifest and
point the CLI or the library at it. If it uses an operator outside the set, loading fails with
a message naming the operator and its index; `tools/oracle/dump_ops.py` lists what a file
contains. Version 1 models are not supported.

## Command line

```sh
go install github.com/tgallice/wakeword-go/cmd/wakeword@latest

# A 16 kHz mono 16-bit WAV file
wakeword detect --model testdata/models/v2/okay_nabu.tflite recording.wav

# Raw PCM on stdin, for instance from a microphone (no CGO: capture is left to ALSA or
# PulseAudio tools)
arecord -f S16_LE -r 16000 -c 1 -t raw | wakeword detect --raw --model okay_nabu.tflite
parec --format=s16le --rate=16000 --channels=1 --raw | wakeword detect --raw --model okay_nabu.tflite

# Options: threshold and window overrides, VAD gating, blocked detections
wakeword detect --model okay_nabu.tflite --cutoff 0.9 --vad vad.tflite --verbose clip.wav

# Watch the raw model output every 30 ms while tuning the microphone gain or the cutoff
wakeword detect --raw --probabilities --model hey_jarvis.tflite < capture.raw

# Dump the 40 frontend features per 10 ms frame (uint16 and int8) for debugging
wakeword features recording.wav
```

Capture gain matters: a clipped input (peaks at full scale) yields a probability of 0 on
every frame, and a very quiet one is not detected either. Aim for speech peaks around
-6 to -3 dBFS, and check with `--probabilities` that the output rises on the wake word.

Each detection prints one line: the time in seconds, the wake word, and the average and
maximum probability over the sliding window. The manifest next to the model provides the
default threshold and window; `--config` selects another one. Direct ALSA access from Go is
out of scope; `arecord` and `parec` cover Linux, and any tool that writes raw 16 kHz mono
16-bit PCM to a pipe works.

## Library

```go
import (
	"fmt"
	"log"
	"os"

	"github.com/tgallice/wakeword-go/wakeword"
)

model, _ := os.ReadFile("okay_nabu.tflite")
manifest, _ := os.ReadFile("okay_nabu.json")
det, err := wakeword.NewDetector(model, manifest, wakeword.Options{})
if err != nil {
	log.Fatal(err)
}
for {
	pcm := nextChunk() // []int16, 16 kHz mono, any length
	events, err := det.Feed(pcm)
	if err != nil {
		log.Fatal(err)
	}
	for _, ev := range events {
		fmt.Printf("%s at %.2fs (avg %d/255)\n", ev.WakeWord, float64(ev.Sample)/16000, ev.AverageProbability)
	}
}
```

`Feed` runs the frontend, the ESPHome feature quantization and the model, and applies the
ESPHome rules: a sliding window of probabilities, a warm-up of 100 feature frames (1 s)
after each reset, and a refractory period of the same length after each detection.
`FeedFeatures` accepts 40 int8 features directly, and the `frontend`, `runtime` and
`kernels` packages are usable on their own. Neither `Feed` nor the interpreter allocates
after construction.

## Measured results on a synthetic corpus

There are no real recordings yet, so the validation corpus is synthetic: every clip
is produced by [Piper](https://github.com/rhasspy/piper) text to speech, the same engine
microWakeWord uses to generate its training data. That makes this test easier than real life
in two ways: the models have seen Piper voices during training, and synthetic speech has none
of the variability of real microphones, rooms and speakers. The numbers below show that the
Go port behaves like the original on the kind of audio the models were built on; they do not
predict recall or false accepts on real voices. The corpus is regenerated with
`tools/corpus/generate.py` (seven Piper voices, three speech rates, gain, added silence and
background noise at 10 to 20 dB SNR):

| subset | content | size |
|---|---|---|
| positive | the wake word alone, 60 clips per word | 240 clips, 11 min |
| embedded | the wake word inside a sentence, 36 per word | 144 clips, 10 min |
| near miss | phonetic neighbours such as "Hey Jervis", "Hey Mike", "Okay Naboo", "Alex" | 288 clips, 14 min |
| negative speech | 207 sentences without any wake word, read by every voice | 100 files, 64 min |
| noise and music | white, pink and brown noise, synthetic chords and drums | 10 files, 10 min |

Results with the manifest threshold and window, with a 3.5 s near-silent preroll before each
file so that the warm-up is over, measured with `go run ./cmd/wakeword-eval` on the corpus
above (exact command in `tools/corpus/README.md`):

| model | cutoff | recall, word alone | recall, embedded | targeted near misses accepted | false accepts per hour, speech | false accepts per hour, noise and music |
|---|---|---|---|---|---|---|
| alexa | 0.90 | 95.0% (57/60) | 97.2% (35/36) | 38.9% | 0.93 (1) | 0 |
| hey_jarvis | 0.97 | 100% (60/60) | 100% (36/36) | 45.8% | 6.54 (7) | 0 |
| hey_mycroft | 0.95 | 76.7% (46/60) | 66.7% (24/36) | 87.5% | 9.34 (10) | 0 |
| okay_nabu | 0.97 | 85.0% (51/60) | 75.0% (27/36) | 33.3% | 1.87 (2) | 0 |

Reading the numbers:

- **Every speech false accept lands on a sentence planted to be confusable.** The 20 false
  accepts across the four models are all on sentences such as "Hey Jervis, the bridge is
  closed" (7 of hey_jarvis's 7), "Hey Michael, dinner is ready" and "Hey Mike, what time is
  it?" (hey_mycroft), "Alexander the Great died in Babylon" (alexa), "Okay Naboo is a planet"
  and "Okay now, everybody quiet" (okay_nabu). On the ordinary sentences, which make up most
  of the 64 minutes, there were no false accepts, and none on noise or music.
- **hey_mycroft is the weakest model** on this corpus: it misses the British `alan` voice
  ten times out of twelve and accepts 87% of its near misses, "Hey Mike" and "Hey my craft"
  being almost the wake word. Lowering its threshold to 0.5 brings recall to 95% at 20 false
  accepts per hour on the adversarial sentences.
- **The VAD model changes nothing here**, because every negative is either speech or has no
  false accepts anyway. Its purpose is to reject non-speech triggers in a real room.
- **Threshold sweep**: the evaluator also runs cutoffs 0.5, 0.8, 0.9, 0.97 and 0.99; recall
  and near-miss acceptance move together, as expected for a single threshold.

The committed fixtures in `testdata/audio` (seventeen clips, under 2 MB) are a fixed subset of
this corpus; `wakeword.TestSyntheticAudioFixtures` asserts the detections and rejections
on them at the manifest settings. A validation on real voices remains to be done and is
listed as such in `docs/plan.md`.

## Performance

Measured with `go test -bench` on an x86-64 desktop, `CGO_ENABLED=0`, single core, no
allocations in any of them:

| stage | per call | share of one core in real time |
|---|---|---|
| frontend, one 10 ms block | 12 us | 0.12% |
| vad model, one invocation (30 ms of audio) | 34 us | 0.11% |
| hey_jarvis | 63 us | 0.21% |
| alexa | 68 us | 0.23% |
| hey_mycroft | 71 us | 0.24% |
| okay_nabu | 78 us | 0.26% |

The kernels are straight ports of the reference C without SIMD or other optimization, by
design: correctness first. That budget is already far below what a wake word needs.

## Layout

```
wakeword/     detector: frontend + model + ESPHome decision logic
frontend/     port of the tflite-micro microfrontend (window, int16 FFT, mel filterbank,
              noise reduction, PCAN, log), 40 uint16 features every 10 ms
runtime/      TFLite model loading, validation, tensors, variables, scheduling
kernels/      the int8 operators and the fixed-point requantization helpers
tflite/       FlatBuffers bindings generated from schema.fbs (TensorFlow v2.18.0)
cmd/wakeword  CLI; cmd/wakeword-eval  corpus evaluator
tools/oracle  Python scripts generating the golden vectors in testdata/
tools/corpus  Python scripts generating the synthetic corpus and picking the fixtures
docs/         spec.md (the technical contract) and plan.md (phases and acceptance criteria)
```

## Regenerating the test data

The golden vectors in `testdata/parity` and `testdata/frontend` come from the reference
implementations, run through frozen Python oracles: LiteRT with the reference kernel
resolver for the models, and `pymicro-features` (the C microfrontend) for the features.
`make oracle` creates the virtual environment and regenerates them with the versions pinned
in `tools/oracle/requirements.txt`. Nothing under `testdata/` is edited by hand.

The synthetic corpus is generated by `tools/corpus/generate.py` into the git-ignored
`tools/corpus/corpus` directory (about 200 MB plus 450 MB of Piper voices), then
`select_fixtures.py` picks the committed subset. See `tools/corpus/README.md`.
